# Eira 实施计划 · 总览与公共约定

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement plans task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 给 Eira 项目提供一份跨所有 Phase 的实施总览，统一约束（测试、提交、依赖、目录结构），并定义"数据验证门（Validation Gate）"格式。每个 phase 的详细计划文件遵循本文档约定，避免重复。

**Architecture:** 见 `docs/superpowers/specs/2026-05-26-architecture-design.md`。

**Tech Stack:** Python 3.11+/FastAPI、Vue 3+Vite+TS、PostgreSQL+pgvector、Redis、OSS、WebSocket、LangGraph、Cubism Web SDK + PixiJS。

## 3. 通用约定

### 3.1 提交粒度

- **每个 Step 5 都是 commit 步骤**：测试通过即提交，不允许多 step 合并提交。
- **commit message 前缀**：`feat:` `fix:` `test:` `refactor:` `chore:` `docs:` `infra:`。
- **不允许 `--no-verify`**；pre-commit hook 失败必须修复后另起新 commit。
- **commit 不带本任务以外的改动**；脏文件先单独 chore 提交。

### 3.2 测试规则

- **TDD 强制**：每个功能 step 1 写失败测试 → step 2 验证失败 → step 3 实现 → step 4 验证通过 → step 5 提交。
- **单元测试**：纯函数、领域服务、capability adapter（mock 外部）。
- **集成测试**：真 PG/Redis（docker-compose），跑 Knowledge Pipeline、Orchestrator 图等。
- **契约测试**：FastAPI 自动生成 OpenAPI，使用 `schemathesis` 做 fuzz；WS 消息 schema 用 Pydantic 校验。
- **前端测试**：Vitest + Vue Test Utils（composable / 关键组件）；Playwright 跑核心 E2E。
- **外部 AI 服务测试**：`pytest-vcr` 录制回放，CI 不消耗真 API key。
- **测试覆盖率门**：后端单元 + 集成合计 ≥ 70% lines，每个领域包关键 service ≥ 80%。低于阈值的 PR 拒绝合入。

### 3.3 代码规范

- **后端**：`ruff` + `mypy --strict`（strict 仅限领域服务、capability、orchestrator 三块；infra 可放宽）。
- **前端**：`eslint` + `vue-tsc --noEmit`。
- **格式化**：`ruff format` + `prettier`。
- **pre-commit hook** 跑 lint + 类型 + 单元测试（轻量子集）。

### 3.4 配置与密钥

- **环境变量** 经 `.env.example` 模板登记；`.env` 不入库。
- **密钥不得出现在**：日志、错误响应、提交、issue、Slack、聊天上下文。
- **本地开发** 使用 `.env.dev`；CI 使用 GitHub/Gitea Secrets。

### 3.5 日志与可观测

- 所有进程使用 `structlog` JSON 格式，字段约定：`ts / level / event / request_id / user_id / latency_ms / extra`。
- 关键节点埋点：Orchestrator 每节点入参摘要 + 耗时；外部 API 调用 provider/model/tokens/cost/latency。
- Phase 0 同时接入 Prometheus `/metrics` 与 healthz。

## 4. 数据验证门（Validation Gate）

**核心机制**：每个 Phase 末尾或重要节点设置一个或多个"验证门"。门未通过 → 不进入下一 Phase；通过 → 提交后续 Phase。

每个验证门包含五要素：

1. **指标（Metric）**：可量化的观测对象
2. **阈值（Threshold）**：通过 / 不通过的硬线
3. **测试方法（Method）**：如何收集数据，必须可复现
4. **数据源（Source）**：日志、指标系统、人工评测、模型评测
5. **分支动作（Branch Action）**：通过怎么走、不通过怎么走（回到哪一步、调哪个参数、是否升级 spec）

模板：

```markdown
#### 🚦 Validation Gate G-X.Y · <名称>

| 项 | 内容 |
|---|---|
| 指标 | <如：首响延迟 P95> |
| 阈值 | <如：< 3s（含 RAG 路径）> |
| 测试方法 | <可复现的步骤；fixture/脚本路径> |
| 数据源 | <Prom 查询 / 日志 grep / 评测脚本输出> |
| 通过分支 | 提交标签 `gate-G-X.Y-passed`；进入下一任务 |
| 不通过分支 | <如：若 P95 在 3-5s，调小 chunk 数；若 > 5s，回到 Task X.N 改异步策略；若可复现失败 → 升级 spec 重审 RAG 节点> |
```

**所有验证门数据**统一记录到 `docs/superpowers/validations/<gate-id>.md`，包括：测试时间、原始数据、判定结论、采取的动作、是否触发 spec 修订。这些文件**必须 commit**，不入 `.gitignore`。

### 4.1 全局红线（任何时候触发都立即停下）

- **API key 泄露**：日志/响应/前端任何一处出现真实 key → 立即吊销 + 全量审计。
- **数据库 schema 破坏性变更**：不能直接 `DROP COLUMN` 已有数据列，需走多步迁移。
- **生产对外接口非兼容变更**：必须双版本过渡。
- **CI 主分支红色**：无新 PR 合入，先修红再继续。

## 5. 迭代回路

**Phase 内**：

```
brainstorm → spec（已有顶层架构 + 子 spec 时，跳过此步）
          ↓
       writing-plans（本套文档）
          ↓
       执行任务（subagent-driven 或 inline）
          ↓
       Validation Gate
          ↓
   通过 → 进入下一 Phase
   不通过 → 修正动作（参见门定义）→ 必要时回到 spec/plan 修订
```

**Spec 修订**：任何 Validation Gate 触发 spec 修订时，须：
1. 在 spec 文件追加 `## Revision <date>` 段，记录原决策、新决策、触发原因；
2. 受影响的 plan 文件追加 `## Revision <date>` 段；
3. 已完成的代码变更如与新 spec 矛盾，列入下个 phase 的"补丁任务"段。

**版本号**：spec/plan 不用 SemVer；只记录 `## Revision <date>` 段。
